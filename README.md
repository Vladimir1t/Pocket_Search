# PocketSearch

Небольшой поисковый HTTP-сервис на Go для объявлений, вакансий или заметок.
Только стандартная библиотека: можно прочитать весь код и понять каждое решение.

## Возможности

- Создание, замена, получение и удаление документов через HTTP.
- Инвертированный индекс: слово → ID документов и взвешенная частота.
- Поиск по всем словам запроса (AND), фильтр категории, ограничение выдачи.
- Ранжирование: совпадение в заголовке весит в три раза больше совпадения в тексте.
- Unicode, русский и английский, нормализация `ё → е`, токены `C++` и `C#`.
  Одиночные `+` и `#` — знаки препинания, а не слова.
- Конкурентные HTTP-запросы; согласованный доступ к документам и индексу через `sync.RWMutex`.
- Сохранение JSON-снимка при каждом изменении и восстановление индекса при старте.
- Тесты поиска, HTTP, перезапуска, ошибки записи (в том числе HTTP 500) и конкурентных запросов; benchmark.
- `make check` (gofmt, vet, тесты с race detector) и GitHub Actions workflow.
- Ограничение размера HTTP-тела, server timeouts и graceful shutdown.

## Запуск

Нужен Go 1.26 или новее. Внешних модулей, баз данных и API-ключей нет.

```sh
go run ./cmd/pocketsearch
```

По умолчанию: `http://127.0.0.1:8080`, данные: `data/documents.json`.
Во втором терминале из каталога проекта:

```sh
sh scripts/demo.sh
```

Примеры настроек:

```sh
go run ./cmd/pocketsearch -addr 127.0.0.1:9090 -data data/demo.json
go run ./cmd/pocketsearch -data ''  # без сохранения на диск
```

Остановка: Ctrl+C. Уже принятые HTTP-запросы получают до 10 секунд на завершение.

## API

| Метод | Путь | Результат |
|---|---|---|
| PUT | `/documents/{id}` | 201 при создании, 200 при замене |
| GET | `/documents/{id}` | Документ или 404 |
| DELETE | `/documents/{id}` | 204 или 404 |
| GET | `/search?q=go&category=jobs&limit=20` | Результаты по убыванию score |
| GET | `/stats` | Количество документов и уникальных токенов |
| GET | `/healthz` | Проверка доступности HTTP-сервиса |

```sh
curl -X PUT http://127.0.0.1:8080/documents/job-1 \
  -H 'Content-Type: application/json' \
  -d '{"title":"Go developer","text":"Удалённая работа с PostgreSQL","category":"jobs"}'

curl --get http://127.0.0.1:8080/search \
  --data-urlencode 'q=go удаленная' \
  --data-urlencode 'category=jobs'
```

В ответе `total` — число всех совпадений, `hits` — до `limit` документов.
Одинаковые score упорядочиваются по ID, чтобы результат был воспроизводимым.
Категория сравнивается точно, с учётом регистра. Она не входит в полнотекстовый индекс.
Лимит: 1–100, по умолчанию 20. Запрос: до 512 байт и 16 уникальных слов.
ID: 1–64 латинских буквы, цифры, `-`, `_`. Тело запроса: до 64 KiB.
`PUT` повторно с тем же ID и содержимым не создаёт дубликаты.
Для `C++` используйте `--data-urlencode`, иначе `+` в query string означает пробел.

## Как устроено

```text
net/http → API → Engine
                  ├── documents: ID → Document
                  ├── postings: term → (ID → weighted frequency)
                  └── JSON snapshot
```

Поиск начинает с самого короткого списка документов среди слов запроса, затем
проверяет остальные слова. Полный проход по коллекции для поиска не нужен.

Учебная формула ранжирования, вариант взвешенного TF-IDF:

```text
tf(term, doc) = 3 * occurrences_in_title + occurrences_in_text
idf(term) = ln(1 + document_count / documents_containing_term)
score(doc, query) = sum(tf(term, doc) * idf(term))
```

Повторяющиеся слова запроса учитываются один раз. IDF считается по всей коллекции
до фильтрации категории. Это не BM25: нормализации длины документа нет.

Читатели держат `RLock`, изменения — `Lock`. При записи сначала создаётся новый
снимок во временном файле в том же каталоге, выполняются `Sync`, `Close`, `Rename`,
затем меняются документы и индекс в памяти. Ошибка сохранения до успешного Rename
не публикует изменение в памяти. При старте некорректный снимок вызывает ошибку,
а не тихое обнуление коллекции.

В обработчиках не создаются дополнительные goroutine ради каждого поиска:
`net/http` уже обслуживает запросы конкурентно. Параллельные поиски допускаются,
записи сериализованы. Отдельная goroutine в main нужна для запуска HTTP-сервера
и обработки сигнала завершения.

## Проверки

```sh
make check   # gofmt + go vet + go test -race
go test -race -count=1 ./...
go vet ./...
go test ./internal/search -run '^$' -bench . -benchmem
go build -o bin/pocketsearch ./cmd/pocketsearch
```

Race detector для этих команд требует поддерживаемую платформу, CGO и C toolchain.
Benchmark использует 1 000 документов и запрос, которому соответствуют 50.
Это измерение локального поиска в памяти, без HTTP и записи на диск.

## Ограничения и компромиссы

- Учебный сервис для небольших коллекций. Каждый update переписывает всю коллекцию
  под write lock: O(N) по объёму данных. Это осознанное упрощение хранения.
- Только один процесс на файл. Межпроцессной блокировки нет.
- Индекс целиком в памяти. В результатах сортируются все совпадения, затем берётся limit.
- Замена файла рассчитана на POSIX/macOS/Linux. Нет гарантии сохранности последней
  операции при отключении питания: каталог после rename не синхронизируется.
- Нет морфологии, исправления опечаток, поиска подстрок и фраз. `разработчик`
  и `разработчика` — разные токены. `Go` и `Golang` — тоже разные токены.
- Нет авторизации и rate limiting. По умолчанию сервер слушает только localhost;
  это локальный demo, а не готовый публичный сервис.
- Нет фоновой индексации: успешный PUT сразу виден в поиске. Очередь и eventual
  consistency здесь не нужны для выбранного масштаба.

## Что разобрать перед собеседованием

1. Проследить путь PUT → сохранение → обновление индекса → Search.
2. Объяснить, почему `map` защищён mutex и почему результат поиска не содержит
   ссылок на изменяемые внутренние map.
3. Объяснить выбор самой редкой posting list и стоимость сортировки совпадений.
4. Показать тест удаления старых токенов при обновлении документа.
5. Показать тест ошибки диска: клиент получает ошибку, индекс остаётся прежним.
6. Запустить race detector и benchmark; записать реальные условия измерения.
7. Объяснить, почему добавление goroutine само по себе не ускоряет эту программу.

## Небольшие самостоятельные продолжения

Выберите одно, чтобы проект стал вашей собственной инженерной работой:

1. **Top-K через heap:** заменить сортировку всех результатов, сравнить benchmark.
2. **SQLite:** заменить полное переписывание снимка транзакциями, сохранить собственный индекс.
3. **Поиск с OR:** добавить режим объединения posting lists и тесты ранжирования.
4. **Версии документов:** отклонять устаревшие обновления и протестировать конфликт.

После изучения и собственной доработки проект можно описать в резюме так:

> Учебный проект PocketSearch на Go: HTTP API поиска объявлений, инвертированный
> индекс, ранжирование с весами полей, сохранение состояния, конкурентный доступ
> через RWMutex, тестирование HTTP и проверка race detector.

Не указывайте коммерческую эксплуатацию, нагрузку или ускорение без реальных измерений.
